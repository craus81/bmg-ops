# FleetSuite Feature Audit — Round 4 (2026-09): the opportunity roadmap

The three defect rounds (see `docs/workflow-audit-2026-08.md`) closed with
nothing open. Round 4 asks the opposite question: **what should this app do
next?** — new features, ranked, with the CEO dashboard as a stated priority.

**Method.** Three orchestrated passes over the code at HEAD (post-#835):
(1) *Understand* — 10 parallel subsystem readers + 4 gap-fill readers + a
completeness critic built a current-state map: every surface per role, every
data asset captured-vs-surfaced, every seam where work leaves the app;
(2) *Generate* — 13 role/discipline lenses plus a dedicated CEO-dashboard
designer produced 133 proposals grounded in that map;
(3) *Verify & rank* — proposals were clustered into 86 candidate features,
each adversarially verified against the code (does it already exist? is the
data really there? honest effort?) with file:line evidence, then ranked.
42 agents total. **No cluster came back 'already exists'** — generation was
grounded in the map, so the whole menu below is real, buildable, new work.

**How to read entries.** *Value* 1–5 (5 = changes how the business runs).
*Effort*: S = one PR · M = 2–3 PRs · L = ~a week of PRs · XL = multi-week.
*N×* = how many independent lenses proposed it (convergence = demand).
*Verdict* from code verification: NEW / MOSTLY NEW (small existing pieces) /
PARTIAL (meaningful existing machinery to build on — effort shown is the delta).

**Ship-first rule regardless of picks:** three tiny capture migrations cannot
be backfilled and should land in week one — the nightly `metric_snapshots`
table, `paid_at` stamping on the A/R sweep, and vendor ETA/receipt event
history. Every week they wait is trend history lost forever.

## Tier 1 — do these first

Highest leverage per effort, anchored on the stated CEO-dashboard priority and capture-before-reporting sequencing. metric-snapshots leads because history cannot be backfilled — every week of delay is trend data lost forever; executive-bands is the CEO view's visible first win (M, mostly rendering, one role-guard fix). order-book-unbilled-revenue (value 5, 3 lenses) is both a top ask and the feeder for CEO Phase 3. exceptions-overrides-digest is effectively S per its own risk note, riding existing audit/cron/email machinery. promised-back-guardian and three-way-match are value-5, 3-lens, M-effort wins. punch-clock-timesheets carries the highest convergence in the whole set (5 lenses) and unblocks crew-utilization and payroll reporting downstream. reorder-points-replenishment is value 5 with 4 lenses; scan-type classification is its only real design work. Eight M-or-smaller items that light up the dashboard's data spine plus the three most-demanded operational wins.

> **Ship log (2026-09-07).** The whole tier was decided and built the day the audit landed, one auto-merged PR per item: metric snapshots **#837**, CEO view Phase 1 **#840**, Order Book **#839**, Exceptions & Overrides Digest **#841**, Promised-Back Guardian + On-Time Scorecard **#842**, Reorder Points & Auto-Replenishment **#843**, Three-Way Match **#844 + #845**. #### Nightly metric snapshots + trend charts
*Value 5/5 · effort M · proposed independently by 1 lens · NEW*
> **SHIPPED — PR #837** (migration 270). `metric_snapshots` + nightly cron at 04:30 UTC computing 14 metrics through `src/lib/exec-metrics.ts`; each metric fails independently (null + error meta, never a lying zero). Sparklines landed with #840. History started accruing 2026-09-08; quoted-margin stamping rides the Tier-2 margin-ledger cluster as specced.

**The problem.** Every financial number is a live read that evaporates at midnight — no A/R-over-time, no backlog trend, no cash trend, and history can never be backfilled: every week unshipped is trend data lost forever.

**The build.** A metric_snapshots table (metric, day, value, meta jsonb) and a nightly cron recording ~12 numbers (cash, A/R buckets, A/P, open-quote $/count, pipeline $, MTD revenue, SO order-book $, unbilled $, vehicles in shop), then sparklines under CEO tiles and four charts (cash 90d, stacked A/R aging 26wk, revenue 13mo, backlog vs unbilled). Also stamp blended quoted margin % on estimates at send. Fed by other clusters: the quoted-margin ledger, days-to-pay/paid_at capture, and order-book clusters each add snapshot metrics; the owner-brief cluster reads week-over-week deltas from this table.

**Data.** Claim is accurate: every input is computed in-app today — computeArAging (src/lib/financials-data.ts), invoiced-summary route, A/P+cash via /api/reports/financials, unbilled math already written in parts-demand.ts:311 ((quantity − quantity_billed)), in-shop counts on OpsDashboard. Two corrections: (1) cash/A-P/card inputs come from the financials RESTlet and are null when it errors (FinancialsData config.balancesOk) — snapshots must record null, not 0, or trends lie; (2) the open-quotes and pipeline queries live client-side in OpsDashboard.tsx and must be ported into the cron server-side. Estimate margin stamping needs a new column + a write in the send-for-approval path.

**Verified against the code.** No metric_snapshots (or any snapshot) table in any of the 286 files in migrations/ (grep 'snapshot' hits only unrelated columns); vercel.json has 15 crons, none nightly-snapshot; no margin columns on estimates — only quote_settings.margin_floor_pct (migrations/150-quote-margin.sql:8). No sparkline/chart component exists (only FinancialsDrilldown matches 'chart' incidentally) and no chart library in package.json.

**Traps & constraints.** History can't be backfilled — the plan doc itself says ship this early. Migration auto-applies on deploy (CLAUDE.md — write idempotent, never hand-apply, verify via Vercel build log 'applied 270-*.sql'). Cron additions edit vercel.json + need CRON_SECRET auth + recordHeartbeat wiring (pattern in stuck-vehicle-check/route.ts:23-29). Charts are hand-rolled SVG (no lib) and must respect the text-size zoom rule (no bare vh/vw). Margin-at-send touches the estimate approval path which carries the sent-hash guard (migration 242) — stamp alongside, don't perturb the hash. Snapshot metrics from phases 3-5 (order book, pnl, payroll) land later — design the (metric, day, value, meta) shape to absorb them without migration churn.

#### Order Book & Unbilled Revenue
*Value 5/5 · effort M · proposed independently by 3 lenses · MOSTLY NEW*
> **SHIPPED — PR #839.** `src/lib/order-book.ts` (one loader for the report, the snapshots, and the CEO band), `/admin/reports/order-book` with aging buckets, billed %, CSV, and NetSuite links. Unbilled = line amount scaled by the unbilled quantity fraction, over-billed lines clamped.

**The problem.** FleetSuite mirrors every NetSuite sales order 2-hourly back to 2024 (netsuite_sales_orders + _lines with status, total, trandate, quantity vs quantity_billed, rate) but the only reader is parts-demand math. 'How much work have we sold that isn't delivered or billed yet?' is unanswerable: backlog value, aging Pending Fulfillment orders, and sold-but-unbilled dollars are invisible; the owner runs NetSuite saved searches or guesses, and revenue leaks surface only at month-end reconciliation, if at all.

**The build.** An /admin/reports/order-book page: total open backlog $ by status (Pending Approval / Pending Fulfillment / Partially Fulfilled / Pending Billing) and by customer; aging buckets for stalled orders (days since trandate); unbilled revenue = Σ(quantity − quantity_billed) × rate with a drill-down of partially billed orders; a 'Pending Billing' lane deep-linked to existing invoice actions ('invoiceable RIGHT NOW'); every row deep-links to the SO in NetSuite and its linked estimate/upfit project. Include a confirm/dismiss review action on weak memo-matched orders (match_source='memo') so the totals are trustworthy. A 'backlog $ / unbilled $' KPI tile joins the dashboard, deltas feed the weekly brief, and the headline numbers render on the CEO view's Operations band (ceo-dashboard Phase 3).

**Data.** Accurate: every needed column exists and is synced 2-hourly; the only schema change is the dismissed/confirmed review flag. Refinements: bucket labels (Pending Approval/Fulfillment/Partially Fulfilled/Pending Billing) map from the letter status codes/status_label — the mapping table must be written (only closed-set classification exists today); line rate can be null (fall back to amount/quantity); confirm on memo-matched rows implies writing estimates.netsuite_so_id, which the sync deliberately refuses to do for memo matches — that write needs the same guards the sync applies (don't overwrite an existing SO id).

**Verified against the code.** No order-book page or API exists: src/app/(main)/admin/reports/ has 9 report dirs (accounting-package … vehicle-margin), none order-book; no unbilled-$ rollup anywhere in src. The data layer is complete and battle-tested: netsuite_sales_orders(status, status_label, trandate, total, estimate_id, match_source) + lines(quantity, quantity_billed, rate, amount) per migrations/196; the exact unbilled formula already written at parts-demand.ts:311; open/closed classification at parts-demand.ts:40-54 (CLOSED_SO_STATUS_CODES C/G/H + label regex); NetSuite transaction deep-link helper at netsuite.ts:634; sync runs 2-hourly (netsuite-sync/route.ts:393). match_source is written by the sync (sales-order-sync.ts:545) but has NO reader in any page — the memo-review confirm/dismiss action is entirely new (new column + route + UI).

**Traps & constraints.** Mirror trust: numbers are up to 2h stale and quantity_billed only refreshes when NetSuite touches lastmodifieddate — label the as-of time (sync_state/system-health already expose it, reuse describeSoMirrorHealth). Reads of netsuite_sales_orders/_lines are unbounded — fetchAllRows + deterministic order is mandatory (repeat field-bug class). The 'invoiceable RIGHT NOW' lane must route through the existing invoice paths only: every SO→invoice path fulfils first via fulfillSalesOrder and uses the invoice_claims idempotence (migrations/251) — do not add a new invoice button that bypasses them (CLAUDE.md owner rule). Review-flag writes on mirror rows survive the sync's upsert only if the flag column is excluded from the upsert payload — verify, or keep dismissals in a side table. Dashboard KPI for executives crosses the staff-read RLS/role boundary — serve it from a guarded route, not a client query.

#### Reorder Points & Auto-Replenishment Sweep
*Value 5/5 · effort M · proposed independently by 4 lenses · MOSTLY NEW*
> **SHIPPED — PR #843** (migration 271). Per-part Reorder At / Up To on /parts, nightly sweep raising tagged `purchase_requests` into /admin/purchasing (AUTO chip, velocity note, one digest for new rows), pending-request netting + demand-dismissal watermarks so it never double-queues or nags past a buying decision. The feared scan-type classification dissolved: `scan_logs` has no type column because every row IS one installed unit — velocity is a row count. Deferred: the reorder-point seeding helper (needs lead-time history that only starts accruing now) and low-stock chips outside the queue.

**The problem.** Ordering is entirely reactive: a shortage exists only when a person opens a readiness card or the demand tab and notices — a missed look means a vehicle stranded in a bay waiting on a $40 bracket, plus rush freight. There are no reorder points, min/max levels, or consumption-based suggestions anywhere, even though the app already knows consumption velocity (scan_logs per-part install counters), live stock (netsuite_parts.quantity_available, 2-hourly), what's inbound (netsuite_vendor_po_lines quantity − quantity_received), reservations (part_allocations), and pending requests — nothing connects them.

**The build.** Add 'Reorder at / order up to' fields per part on /parts (admin-edited like labor_hours; per-part opt-out; parts with no point set are untouched). A nightly cron computes each flagged part's trailing-90-day consumption velocity from scan_logs (paginated via fetchAllRows), free stock (available − allocations), and open on-order; when projected cover (weeks-of-stock) drops below the point, it raises a purchase_request tagged 'auto-reorder' with suggested qty = order-up-to − (free + on-order), deduped against pending requests and demand dismissals, landing in the existing /admin/purchasing queue with the usual ?req= deep-link notification. The sweep can also fold in the demand-tab math (open SO lines + approved un-converted estimates) as a second signal. A 'suggest a reorder point' helper (velocity × typical lead time) seeds points for top-moving parts so setup isn't 3,000 manual entries; low-stock chips appear on the inventory page and readiness cards. Purchasing keeps final say — the sweep queues, it never cuts POs.

**Data.** partial as claimed, with two additions: (1) purchase_requests has NO source/tag column (migration 240 columns: item_number…requested_by) — tagging rows 'auto-reorder' needs a migration, not just a string; (2) vendor lead time confirmed absent — no ETA history table exists and po_receipts (241) only accrues from ~Aug 2026, so the 'suggest a reorder point' helper genuinely starts on a default lead-time constant.

**Verified against the code.** Grep for reorder_point|order_up_to|replenish over the whole repo: zero hits. ## Sequencing, batches, and house rules

Themes and sequencing. (1) Capture-before-reporting is the round's backbone: three tiny migrations should ship in week one regardless of tier — metric snapshots (ceo-phase2), paid_at capture (days-to-pay), and vendor-event capture (vendor-scorecards) — because none can be backfilled; each week of delay is history lost. (2) The CEO dashboard builds in its plan's order: Phase 1+2 now, Phase 3 rendered over order-book-unbilled-revenue (count the API effort once, in the feeder cluster), Phase 4 scheduled around a human hand-deploying the RESTlet, Phase 5 gated on an owner phone call, Phase 6 unified with owners-weekly-brief into one composer — building both separately is the round's clearest duplication trap. (3) punch-clock-timesheets is the highest-convergence item (5 lenses) and the gateway to crew-utilization, labor-burn, and payroll export — its RLS/approve-lock work pays off three times. (4) Natural PR batches: the purchasing set shares tables and the demand tab; the CNI set should share one cron sweep; the sales set all touches the 4000-line estimate builder and status='sent' semantics, so sequence those to avoid merge pain; portal items reuse one token/audience pattern. (5) Recurring house rules the risks keep citing — fetchAllRows for any unbounded read, idempotent auto-applying migrations, approval_rate_limits on every new public endpoint, E-SIGN hash/snapshot discipline on anything touching approval links, and m171's opt-in email default — treat these as acceptance criteria on every cluster above. (6) Tier 4 is decision-blocked, not engineering-blocked: two-way-customer-inbox and carrier-tracking-autopilot both have strong multi-lens demand and jump to Tier 2 the day the owner makes the Reply-To policy call or provisions the aggregator account.

## The CEO Dashboard — full design spec

**Relationship to `docs/ceo-dashboard-plan.md`:** this spec HONORS that plan — its scorecard, its two structural unlocks (extend the financials RESTlet for P&L; Paychex for payroll/headcount), and its "snapshot early because history can't be backfilled" insight are all kept. It IMPROVES the plan in four ways: (1) the plan's Phase-1 item 1 (open-quotes tile bug) has already shipped — OpsDashboard now merges `wrap_quotes` + `estimates` — so it drops out; (2) the plan is finance-only and ignores the operational data only this app holds — the `netsuite_sales_orders` mirror (full order book, per-line `quantity_billed`, read today only by parts-demand math), the three status-history ledgers (zero cycle-time reporting), and the per-vehicle margin report — so this spec adds an **Operations band** that gives the owner throughput and backlog, not just balances; (3) quoted margin is computed live in the estimate builder and discarded — persisting it gives a *leading* gross-margin indicator months before the P&L unlock lands; (4) the plan never says how the dashboard reaches the owner — this spec adds a scheduled Monday email digest, because today every report in the app is pull-only.

**Where it lives:** extend the existing Home → Financials tab (`FinancialsDashboard.tsx`, `executive`/`super_admin` via `requireFinancials`, migration 176 built the `executive` role exactly for this) into a multi-band "CEO view" rather than a new page — the owner's login already lands there, drill-downs and statement printing already work there, and one URL means one habit.

**Cadence model:** two data paths. *Live* = read-through to NetSuite/Supabase on open (what Financials does today, `CACHE_TTL` cached). *Nightly snapshot* = a `metric_snapshots` row per metric per day written by a cron (same daily-cron pattern as `at-risk-check` in vercel.json); every trend chart reads snapshots, every "now" number reads live. Rule: a tile shows the live number, its sparkline shows snapshots.
